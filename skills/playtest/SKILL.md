# playtest

분석과 구현을 가른다. 원인을 찾는 일은 비싼 모델이 한 번 하고 문서로 남긴다. 고치는 일은 그 문서를 읽은 싼 모델이 한다.
문서가 사이에 있으므로 구현 세션은 대화 기록 없이 새로 열어도 된다.

| 호출 | 뜻 |
|---|---|
| `/gamedev-kit:playtest <문제 목록>` | 분석. 문서를 만들고 멈춘다 |
| `/gamedev-kit:playtest implement [문서]` | 구현. 문서를 생략하면 `docs/playtest/` 의 가장 새 문서 |
| `/gamedev-kit:playtest status` | 문서들의 남은 작업 |

## 분석

1. **목록을 받는다.** 사용자가 적은 문장을 다듬지 않는다. 목록이 메시지에 없으면 달라고 한다.
   어느 빌드(커밋)에서 본 것인지 모르면 `git rev-parse --short HEAD` 로 지금 것을 적고, 커밋 안 된 변경이 있으면 알린다.
2. **`gamedev-kit:playtest-analyst` 에이전트에게 맡긴다.** 넘길 것: 문제 목록 원문 그대로, 커밋 해시,
   사용자가 덧붙인 맥락(어느 장면 · 어느 기기 · 몇 번 해 봤는지). **네 추측은 넘기지 않는다** — 가설을 받은 분석가는 그 가설을 확인해 온다.
   에이전트는 모델이 정해져 있다. 여기서 직접 분석하지 않는다 — 이 스킬의 요점이 그것이다.
3. **돌아오면** 문서 경로, 작업 수, "사용자에게 물을 것" 을 그대로 전한다. 질문이 있으면 답을 받아 문서의 그 자리에 적는다.
4. **멈춘다.** 구현으로 넘어가지 않는다. 사용자가 문서를 읽고, 모델을 바꾸고(또는 새 세션을 열고), implement 를 부른다.
   끝에 한 줄로 알린다: 구현은 더 싼 모델로 바꿔 `/gamedev-kit:playtest implement` 를 부르면 된다고.

## 구현

1. 문서를 읽는다. "사용자에게 물을 것" 에 답이 안 적힌 질문이 있으면 그 질문에 걸린 작업은 건너뛰고, 건너뛴다고 말한다.
2. **"순서" 대로 한 작업씩.** 작업마다:
   - "고칠 곳" 을 먼저 열어 문서가 말한 코드가 아직 그대로인지 본다. 문서는 분석한 커밋의 사진이다 — 달라졌으면 멈추고 알린다.
   - 적힌 대로 고친다. "건드리지 말 것" 을 지킨다. 문서에 없는 개선은 하지 않는다.
   - "확인" 의 자동 부분을 돌린다. 사람이 봐야 하는 부분은 모아 둔다.
   - 통과하면 문서의 `### [ ]` 를 `### [x]` 로 바꾸고, 문서와 다르게 한 것이 있으면 작업 아래 `- **한 것**:` 한 줄로 적는다.
3. **문서가 틀렸으면** (원인이 다르다 · 고칠 곳이 없다 · 고쳐도 확인이 실패한다) 스스로 다시 분석해 밀고 가지 않는다.
   그 작업을 `### [!]` 로 표시하고 무엇을 봤는지 적은 뒤 다음 작업으로 간다. 다시 분석할지는 사용자가 정한다.
4. 분류가 **설계**인 작업은 사용자의 결정이 문서에 적혀 있을 때만 한다.
5. 분류가 **밸런스**인 작업은 값 파일을 고치고 balance-table 스킬로 `export` 한다 (표가 옛 값을 쥐고 있지 않게).
6. **마지막에** `/gamedev-kit:gdd-sync to-gdd` (값 · 규칙이 바뀌었으면), 그리고 보고:

   ```
   ## 플레이테스트 구현 — <문서>
   - 끝낸 것: T3, T1 · 막힌 것: T2 (이유) · 건너뛴 것: T4 (질문 대기)
   - 직접 해 보고 확인할 것: <작업별로 무엇을 보면 되는지>
   ```

## status

`docs/playtest/*.md` 마다 `[x]` · `[ ]` · `[!]` 수와 답 없는 질문 수를 한 줄씩.

## 문서는 남긴다

끝난 문서도 지우지 않는다. 다음 플레이테스트에서 같은 문제가 다시 나오면 분석가가 이전 문서를 읽고 "지난번에 이렇게 고쳤는데 왜 또" 부터 시작할 수 있다.
