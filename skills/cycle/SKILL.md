# cycle

한 사이클은 **목표 하나를 플레이어 손에 닿게 하는 데까지**다. 단계마다 맡은 에이전트가 일하고, 결과는 사이클 문서 하나에 쌓인다 —
뒤 단계는 앞 단계의 절을 읽는다. **이 세션은 지휘만 한다.** 여기서 디자인하거나 코드를 읽고 고치면 가른 뜻이 없어진다.

**정하는 사람은 사용자다.** 대신 정해 주는 에이전트는 없다. 에이전트는 "결정할 것" 을 선택지와 권하는 것 하나로 돌려주고,
이 스킬은 그것을 모아 묻고, 답을 문서의 "결정" 절에 사용자의 말 그대로 적는다. 답이 없는 결정에 걸린 일은 하지 않는다.

| 호출 | 뜻 |
|---|---|
| `/gamedev-kit:cycle <목표>` | 새 사이클. 디자인과 계획까지 하고 결정을 묻는다 |
| `/gamedev-kit:cycle next` | 가장 새 사이클의 다음 단계 |
| `/gamedev-kit:cycle status` | 사이클마다 지금 단계 · 남은 작업 · 답 없는 결정 |

## 단계

| | 단계 | 누가 | 문서의 절 | 멈추는 곳 |
|---|---|---|---|---|
| 1 | 목표 | 사용자 | 목표 | |
| 2 | 디자인 | `gamedev-kit:designer` `design` | 디자인 | |
| 3 | 계획 | `gamedev-kit:developer` `plan` | 작업 · 순서 | **결정을 묻는다** |
| 4 | 구현 | `gamedev-kit:developer` `build T<n>`, 작업마다 하나 | 작업의 체크 | |
| 5 | 플레이 | 사용자 (문제는 `/gamedev-kit:playtest`) | 플레이 | **내보낼지 묻는다** |
| 6 | 배포 | deploy 스킬 | 배포 | |
| 7 | 홍보 | promo 스킬 | 홍보 | |
| 8 | 회고 | 이 세션이 적고 사용자가 고친다 | 회고 | **다음 목표는 사용자가 정한다** |

### 1. 목표

사용자의 말을 다듬지 않고 "목표" 에 적는다. 목표가 여러 사이클 크기로 보여도 줄이지 않는다 — 줄일지는 계획 단계에서 선택지로 묻는다.
`docs/cycle/NN-<짧은-이름>.md` 를 아래 틀로 만든다 (NN 은 있는 문서 다음 번호). 지금 커밋을 적고, 커밋 안 된 변경이 있으면 알린다.
앞 사이클의 "회고" 에 "다음에" 가 있으면 사용자에게 한 줄로 상기시킨다.

### 2. 디자인 · 3. 계획

디자이너를 부르고, 돌아오면 개발자를 `plan` 으로 부른다. 넘길 것은 사이클 문서 경로와 모드뿐이다. 네 생각을 붙이지 않는다.
디자인 절의 "필요한 에셋" 에 없는 3D 모델이 있으면 사용자에게 알린다 — 만들지(asset 스킬), 임시 에셋으로 갈지는 결정으로 묻는다.
만들기로 하면 구현과 나란히 asset 스킬의 절차를 따른다. 이미지 승인은 그 스킬에서 사용자가 한다.

둘이 돌려준 "결정할 것" 을 번호를 이어(D1 …) 문서의 "결정" 에 `[ ]` 로 적고 사용자에게 한 번에 묻는다 —
선택지 · 각각이 드는 일 · 권하는 것. 그리고 작업 수와 차수를 보여 준다. **여기서 멈춘다.**

답이 오면 `- [x] D1. <질문> → <사용자의 말 그대로>` 로 적는다. 답이 디자인이나 계획을 바꾸면(범위를 줄였다 · 다른 안을 골랐다)
그 에이전트를 다시 불러 절을 고치게 한다. 사용자가 계획을 직접 고쳐 달라고 한 것도 마찬가지다.

### 4. 구현

차수마다, 작업 하나에 개발자 에이전트 하나. 같은 차수는 한 메시지에서 한 번에 부른다. `- **대기**: D<n>` 이 붙은 작업은 그 결정에 답이 있을 때만 한다.
돌아온 결과로 문서를 고친다 (에이전트는 문서를 고치지 않는다): 끝 → `[x]`, 막힘 · 실패 → `[!]` 와 `- **막힘**:` 한 줄.
막힌 작업을 여기서 직접 고치지 않는다 — 막힌 이유를 붙여 `plan` 을 다시 부를지 사용자에게 묻는다.

모든 차수가 끝나면 한 번에: 값 · 규칙이 바뀌었으면 `/gamedev-kit:gdd-sync to-gdd`, 밸런스 값 파일이 바뀌었으면 balance-table 스킬의 `export`,
프로젝트의 검증(CLAUDE.md 의 "검증") 전체. 그리고 사용자에게 플레이해 볼 것을 작업의 "사람이 볼 것" 과 디자인의 "사람이 봐야 아는 것" 에서 모아 전한다.

### 5. 플레이

사용자가 한다. 문제 목록이 오면 `/gamedev-kit:playtest` 로 넘기고, 그 문서 경로를 "플레이" 절에 적는다.
스크린샷을 주면 디자이너를 `review` 로 불러 볼 수 있다. 몇 번을 돌아도 된다.
**내보낼지는 사용자가 말한다.** 묻되 권하지 않는다 — 남은 `[ ]` · `[!]` 작업과 열린 플레이테스트 문서가 있으면 그것만 사실로 알린다.

### 6. 배포 · 7. 홍보

사용자가 내보내자고 하면 deploy 스킬의 절차를 따른다. 그 말이 준비까지의 승낙이고, 올리기 전에 대상 · 버전 · 크기를 보여 주고 받는 답이 올리기의 승낙이다.
올라가면 promo 스킬의 절차를 따른다 — 사이클 문서 경로와 itch.io 주소를 넘긴다. 배포하지 않는 사이클(안에서만 도는 판)이면 둘 다 건너뛰고 그렇게 적는다.

### 8. 회고

"회고" 절을 적는다 — 사실만: 목표 중 된 것과 안 된 것, 막혔던 작업과 이유, 플레이테스트를 몇 번 돌았는지, 미룬 것.
그 아래 "다음에" 에 미룬 것과 플레이에서 나온 것을 후보로 늘어놓는다. 고르지 않는다.
엔진 설정을 손으로 했거나 함정에 걸렸으면 프로젝트의 CLAUDE.md 에 적을지 묻는다.

## 사이클 문서

```markdown
# 사이클 NN — <짧은 이름>

시작: <날짜> · 커밋 <해시 7자> · 단계: 목표

## 목표
사용자의 말 그대로.

## 결정
- [ ] D1. <질문> — ① … ② … · 권함: ① (누가 권했는지: 디자인 | 계획)
- [x] D2. <질문> → <사용자의 답 그대로> (<날짜>)

## 디자인
## 작업
## 순서
## 플레이
## 배포
## 홍보
## 회고
```

머리의 `단계:` 는 단계가 바뀔 때마다 고친다. `next` 와 `status` 는 그 줄을 읽는다.

## next

가장 새 문서의 `단계:` 를 보고 이어 간다. 멈추는 곳(결정 · 내보낼지)에 서 있으면 다시 묻는다 — 답 없이 넘어가지 않는다.

## status

`docs/cycle/*.md` 마다 한 줄: 단계 · 작업 `[x]`/`[ ]`/`[!]` 수 · 답 없는 결정 수.

## 문서는 남긴다

끝난 사이클 문서도 지우지 않는다. 다음 사이클의 디자이너와 개발자가 앞 사이클의 결정을 읽고 같은 질문을 다시 하지 않는다.
